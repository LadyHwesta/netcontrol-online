## Low Priority

### In-memory cache and rate limiter won't survive multiple workers
The DMR/APRS relay-push cache (`_dmr_push_cache`/`_aprs_push_cache`, in `routers/digital_voice.py`/`routers/aprs.py`) and `slowapi`'s rate limiter (`routers/deps.py`) both hold their state in an in-memory Python dict, scoped to a single process. `deploy.sh`/the systemd unit run exactly one `uvicorn` process today (no `--workers N`), so this is currently harmless — there's no second worker for it to be out of sync with.

The moment this ever runs with multiple workers or multiple instances behind a load balancer, both break in different ways: the relay caches become per-worker (a push landing on worker 1 isn't visible to a request served by worker 2 until it falls back to the DB-backed `SystemSetting` copy — stale but not wrong), while the rate limiter becomes per-worker too, which quietly multiplies every configured limit by worker count (e.g. `5/minute` on `/auth/register` becomes ~15–20/minute across 3-4 invisible counters) — that one's a real correctness gap, not just a performance nit.

`slowapi` has a built-in Redis storage backend for exactly this case, so Redis (not something like LSCache, which is a LiteSpeed-web-server page cache and doesn't fit a FastAPI backend unless deployed behind LiteSpeed specifically) would be the natural fix — but it's a real operational dependency (another service to run/monitor/secure) not worth taking on for a single-process, club-scale deployment. Revisit only if/when `--workers N` or multiple instances actually get adopted.

### UI translation (argos-translate) covers auth/nav/Nets/Sessions/Check-In so far, not the rest of the app
The translation framework itself (`routers/translation.py`, `static/js/i18n.js`, the admin Languages tab, `extract_i18n_strings.py`) is complete and works end-to-end. Coverage is being extended incrementally, one real-estate slice at a time: the auth/login screen and shared sidebar nav, the Nets view (`nets.js`/`index.html`'s `#view-nets`), Sessions/Schedule's static chrome (`sessions.js`/`schedules.js`/`index.html`'s `#view-session`), `checkins.js` in full (the check-in roster, CSV import, callsign lookup/search, offline queue banner, Expected Stations, the whole ARES/ACES Tactical Assignments & Station Schedule workflow, the zone roster, traffic message log, and station remarks — added `tn(n, singular, plural)` to `i18n.js` for count-based text along the way, see its own doc comment for the "English one/other split only, not full per-language plural rules" limitation), and finally `sessions.js`'s/`schedules.js`'s own remaining dynamic rendering (2026-08-31: the session-list table, session-summary modal, upcoming-slots sign-up/assign grid). Everything else is still plain hardcoded English:

- **`admin.js`** — the whole admin panel (Operators, Branding, Email, Net Repository, DB Stats, Announcements, Reassign tabs), including its own ternary-composed strings, not started at all.
- **`history.js`, `dmr.js`, `aprs.js`** — their actual dynamic rendering (DMR heard-list, APRS map details/popups, the History view's report tables/CSV presets) — the Sessions/Schedule slice only covered these panels' static headers in `index.html`, not their JS-rendered contents.
- **`admin.html`/`help.html`/`tokens.html`/`report.html`** — static markup beyond the shared nav, not started.
- **`directory.html`/`public.html`** don't even load the shared JS helper files (`state.js`/`utils.js`/`i18n.js`) — they're self-contained pages with their own inline scripts. Wiring in translation there is a separate, smaller effort (they got the pre-paint `<html lang>` script as part of this work, but not `t()`/the switcher).
- Server-side error messages returned from API calls (e.g. `toast(e.message, 'error')` where `e.message` is the raw response body) are **not** translated — only the client-side UI-chrome strings around them are. Translating validation/error responses would mean routing them through `translate_cached` on the backend, a separate piece of work.
- Re-run `python3 extract_i18n_strings.py` after each batch of new `t()`/`tn()`/`data-i18n` call sites, so an admin's "enable a language" bulk pre-translate stays comprehensive.

- ~~Single-file backend (`main.py`)~~ — split the ~5,800-line, ~150-route-handler `main.py` into a `routers/` package: 17 domain modules (`auth`, `orgs`, `nets`, `sessions`, `checkins`, `tactical`, `evac_zones`, `expected_stations`, `traffic`, `history`, `callsign_lookup`, `schedules`, `digital_voice`, `aprs`, `admin`, `public`, `support`) wired up via `app.include_router(...)`, plus `routers/deps.py` (auth/db/rate-limit dependencies), `routers/schemas.py` (the handful of Pydantic models genuinely shared across 2+ routers — `UserOut`, `AdminUserOut`, `OrganizationOut`, `NetOut`, `CheckinOut`), and `routers/helpers.py` (shared non-auth helpers — email/SMTP, CAPTCHA verification, the generic settings store, org bootstrap, and the net/session access-control helpers like `_get_editable_net`/`_get_session_for_user`). `main.py` itself shrank to ~215 lines: logging config, app/lifespan/middleware/static-mount assembly, the 17 `include_router` calls, and the handful of frontend/SPA-shell routes that don't belong to any one domain. Two real cross-section couplings the split surfaced got fixed outright rather than left as awkward cross-router imports: the checkin traffic-toggle endpoints, previously defined under the "Evacuation Zone routes" banner despite being checkin endpoints, moved into `checkins.py`; and Net Schedules + Net Control Signups (which shared `SignupCreate`/`SignupOut`/`DAYS`/`_signup_to_out`) were merged into one `schedules.py` instead of split. The bigger discovery: a wide swath of the test suite controls app behavior via `monkeypatch.setattr(main, "SOME_CONSTANT_OR_FUNCTION", ...)` — SMTP config, CAPTCHA config, `_verify_turnstile`/`_verify_recaptcha`, `send_email` itself. Since a Python function resolves module-level names from `__globals__` at call time (the module it's *defined* in, not wherever it's imported from), moving that code out of `main.py` silently broke every one of those patches — the fixture would still patch a name, just not the one any code path actually read anymore. Fixed by (1) retargeting `tests/conftest.py`'s fixtures and a handful of test files (`test_captcha.py`, `test_email_send.py`, `test_support.py`, `test_aprs.py`, `test_dmr.py`) to patch `routers.helpers`/`routers.<domain>` directly instead of `main`, and (2) for `send_email` specifically — called from many different router modules, not just one helpers-internal function — switching every caller to qualified `helpers.send_email(...)` access (`from routers import helpers`) rather than a bare `from routers.helpers import send_email`, so one patch at the real definition site is observed everywhere regardless of which router the call originates from. All 515 tests pass unchanged in substance (only their patch targets moved); live-verified against a real `uvicorn` process — register → login → create net → session → check-in → history → APRS/DMR config, plus every frontend/public page — with zero duplicate route registrations across the 139 registered routes (2026-08-30)
