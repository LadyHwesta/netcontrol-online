## Low Priority

### UI translation (argos-translate) covers everything except the Changelog/Guide prose
The translation framework itself (`routers/translation.py`, `static/js/i18n.js`, the admin Languages tab, `extract_i18n_strings.py`) is complete and works end-to-end. Coverage was extended incrementally, one real-estate slice at a time: the auth/login screen and shared sidebar nav, the Nets view, Sessions/Schedule, `checkins.js` in full (added `tn(n, singular, plural)` to `i18n.js` for count-based text along the way — see its own doc comment for the "English one/other split only, not full per-language plural rules" limitation), the whole Admin page, the History view + DMR/APRS dynamic rendering, Account (`tokens.html`/`tokens.js`), Report/Request (`report.html`/`report.js`), Help's navigational chrome (2026-08-31), and finally `directory.html`/`public.html` (2026-09-01) — both self-contained standalone pages that previously loaded none of the shared JS helpers at all; they now load `state.js`/`utils.js`/`i18n.js` (removing their own local `const API`/duplicate declarations that would otherwise collide), get the same fixed-corner language switcher the pre-login screen uses (no `#app` header to live in yet), and have every static string plus their JS-rendered list/detail/empty-state content wrapped. `aprs-map.js`'s local `_t = typeof t === 'function' ? t : (s => s)` fallback (from the same slice this page's own translation was deferred out of) now resolves to the real `t()` on `public.html` since `i18n.js` loads before it. One thing was deliberately left out, not missed:

- **`help.html`'s Changelog entries and each Guide section's full prose body** — only the headings/navigation are wrapped. The changelog specifically is a historical record that grows with every shipped feature (every entry ever written, forever) — machine-translating that whole and ever-growing corpus isn't a good use of the pre-translation budget the way live, current-facing UI is. Revisit only if a real non-English-speaking user asks for it specifically; headings alone already make the page navigable.
- When wrapping a lookup table in `t()` (badge-status maps, etc.), build it inside the render function rather than as a module-level `const` — a module-level object literal is evaluated once at script load, before any language is even selected, and its `t()`-translated values would stay frozen at whatever `currentLang` was then. Hit this once already (`admin.js`'s `LANG_STATUS_BADGE`, fixed by turning it into a function called fresh on every render) — worth grepping for `^const.*t(` before calling coverage of a file complete.
- A page's own JS-rendered content (list/detail views built via template literals, not `data-i18n`) can briefly paint in English on first load even once a language is chosen: `syncLangFromUser()` and the page's own data-fetch both fire on boot without waiting on each other, so whichever resolves first wins that render. `translatePage()` (run once `syncLangFromUser` finishes) only re-applies to `data-i18n` elements, not already-rendered template-literal HTML — a subsequent re-render (a poll tick, a filter/search interaction, a manual reload) always shows the correct language. Pre-existing across the whole app (confirmed the main app's own `enterApp()` has the identical race between `syncLangFromUser()` and `loadNets()`), not something introduced by any one slice — worth a proper fix (e.g. `await syncLangFromUser()` before the first render) if it turns out to bother real users.
- Server-side error messages returned from API calls (e.g. `toast(e.message, 'error')` where `e.message` is the raw response body) are **not** translated — only the client-side UI-chrome strings around them are. Translating validation/error responses would mean routing them through `translate_cached` on the backend, a separate piece of work.
- Re-run `python3 extract_i18n_strings.py` after each batch of new `t()`/`tn()`/`data-i18n` call sites, so an admin's "enable a language" bulk pre-translate stays comprehensive.

### No automated check that a shared asset's `?v=N` stays in sync across every page that loads it
Hit this twice in one session (2026-09-01): `index.html` referencing a stale `admin.js?v=40` while `admin.html`/`static/sw.js` had already moved to `v42`, and separately `admin.html`/`help.html`/`tokens.html`/`report.html` all stuck on old `app.css`/`state.js`/`utils.js` versions while `index.html`'s had moved on. Neither broke anything obviously online (`StaticFiles` ignores the query string — it's the same file underneath regardless of which `?v=N` a page asks for), but both meant the offline app-shell precache (`static/sw.js`'s `PRECACHE_URLS`, an exact-URL-match list) silently stopped covering those pages' real requests — invisible until specifically testing offline behavior, which is what surfaced both. The current mitigation is a comment at the top of `static/sw.js` telling whoever bumps a shared file's version to also update it everywhere else that file is referenced, checked only by manual `grep`/a one-off Python script each time a shared file changes — the same "kept in sync by hand, easy to forget" failure mode `migrate.py` was built to eliminate for schema changes. Worth a small pytest test (or a maintenance script, same style as `extract_i18n_strings.py`) that parses every HTML page's static asset references and cross-checks them against `PRECACHE_URLS`, failing loudly on any mismatch — would have caught both incidents automatically instead of relying on someone happening to test offline mode.

### No test coverage for the instance-wide branding logo endpoints
`POST`/`DELETE /admin/branding/logo` and the public `GET /logo` (routers/orgs.py) have never had test coverage, unlike their per-org counterparts (`POST`/`DELETE /orgs/{id}/logo`, `GET /orgs/{id}/logo` — issue follow-up, 2026-09-01) which do, following the exact same pattern (`tests/test_organizations.py`'s `TestOrgLogo`, a small fake-bytes multipart upload). Noted twice in commit messages while building the per-org version and never fixed at the time. Not urgent — these are simple, low-risk endpoints (upload/delete/serve a file) — but worth closing to match the per-org ones now that the pattern to copy exists.

- ~~Single-file backend (`main.py`)~~ — split the ~5,800-line, ~150-route-handler `main.py` into a `routers/` package: 17 domain modules (`auth`, `orgs`, `nets`, `sessions`, `checkins`, `tactical`, `evac_zones`, `expected_stations`, `traffic`, `history`, `callsign_lookup`, `schedules`, `digital_voice`, `aprs`, `admin`, `public`, `support`) wired up via `app.include_router(...)`, plus `routers/deps.py` (auth/db/rate-limit dependencies), `routers/schemas.py` (the handful of Pydantic models genuinely shared across 2+ routers — `UserOut`, `AdminUserOut`, `OrganizationOut`, `NetOut`, `CheckinOut`), and `routers/helpers.py` (shared non-auth helpers — email/SMTP, CAPTCHA verification, the generic settings store, org bootstrap, and the net/session access-control helpers like `_get_editable_net`/`_get_session_for_user`). `main.py` itself shrank to ~215 lines: logging config, app/lifespan/middleware/static-mount assembly, the 17 `include_router` calls, and the handful of frontend/SPA-shell routes that don't belong to any one domain. The bigger discovery: a wide swath of the test suite controls app behavior via `monkeypatch.setattr(main, "SOME_CONSTANT_OR_FUNCTION", ...)` — SMTP config, CAPTCHA config, `_verify_turnstile`/`_verify_recaptcha`, `send_email` itself. Since a Python function resolves module-level names from `__globals__` at call time (the module it's *defined* in, not wherever it's imported from), moving that code out of `main.py` silently broke every one of those patches — the fixture would still patch a name, just not the one any code path actually read anymore. Fixed by (1) retargeting `tests/conftest.py`'s fixtures and a handful of test files (`test_captcha.py`, `test_email_send.py`, `test_support.py`, `test_aprs.py`, `test_dmr.py`) to patch `routers.helpers`/`routers.<domain>` directly instead of `main`, and (2) for `send_email` specifically — called from many different router modules, not just one helpers-internal function — switching every caller to qualified `helpers.send_email(...)` access (`from routers import helpers`) rather than a bare `from routers.helpers import send_email`, so one patch at the real definition site is observed everywhere regardless of which router the call originates from. All 515 tests pass unchanged in substance (only their patch targets moved); live-verified against a real `uvicorn` process — register → login → create net → session → check-in → history → APRS/DMR config, plus every frontend/public page — with zero duplicate route registrations across the 139 registered routes (2026-08-30)
